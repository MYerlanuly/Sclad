## Критичные и важные риски

### 1. ~~Миграции БД не выполняются при запуске через gunicorn/uwsgi~~ (исправлено)
**Где:** Раньше миграции вызывались только в `if __name__ == "__main__":`.
**Исправление:** Миграции вызываются в конце `create_app()` при старте приложения (в т.ч. при запуске через gunicorn). Если БД ещё не создана, миграции не выполняются — первый запуск или `flask init-db` создаёт БД по `schema.sql`.
**Примечание:** При нескольких воркерах каждый при первом запросе выполнит миграции; функции миграций идемпотентны, возможна кратковременная блокировка SQLite.

### 2. ~~Нет защиты от CSRF~~ (исправлено)
**Исправление:** Подключён Flask-WTF (CSRFProtect). Во все POST-формы добавлено поле `csrf_token`. Запросы без валидного токена возвращают 400.

### 3. ~~Блокировка входа по IP хранится в памяти~~ (исправлено)
**Исправление:** Таблица `login_attempts` (ip, count, lock_until); миграция `migrate_login_attempts()`. Счётчик и блокировка общие для всех воркеров.

### 4. ~~Резервное копирование: путь к директории не проверяется~~ (исправлено)
**Исправление:** Разрешена только директория внутри `BACKUP_ROOT` (папка `backups` в корне приложения). При сохранении настроек путь проверяется через `_is_allowed_backup_path()`; при неверном пути показывается сообщение и старое значение не перезаписывается.

### 5. ~~Дублирование бэкапа при нескольких воркерах~~ (исправлено)
**Исправление:** Перед созданием копии захватывается файловая блокировка `_acquire_backup_lock()` (файл в temp, таймаут 60 с, устаревший lock > 5 мин снимается). Только один процесс на машину выполняет бэкап в данный момент.

## Потенциальные ошибки в коде

### 6. Использование `.get()` на объектах, которые могут быть sqlite3.Row
**Где:** В разных местах используется `row.get()`, `m.get()`, `rec.get()`; часть данных приходит как `dict` после явного `dict(row)`, но не везде.
**Риск:** Если в новом коде передать в шаблон или в функцию Row вместо dict, возникнет `AttributeError: 'sqlite3.Row' object has no attribute 'get'`.
**Рекомендация:** Либо везде после `fetch_one`/`fetch_all` приводить к `dict` (например, хелпер `def row_to_dict(row): return dict(row) if row else None`), либо в шаблонах использовать только `[]` и проверки на наличие ключа.

### 7. Сессия Flask и «Недавние»
**Где:** В `session["recent"]` хранятся до 10 элементов с полями type, id, label.
**Риск:** По умолчанию сессия Flask — подписанная cookie; при большом объёме данных cookie может превысить лимит браузера (4 KB).
**Рекомендация:** Следить за размером (10 записей × ~50 символов — в пределах нормы) или перейти на server-side сессию (Flask-Session и т.п.), если список расширять.

### 8. ~~Роль в User и _user_role~~ (исправлено)
**Исправление:** `_user_role(row)` принимает и Row, и dict: используется `try: row.get("role") except AttributeError: row["role"]`. Добавлен хелпер `row_to_dict(row)` для единообразного приведения Row к dict.

## Рекомендации по надёжности

### 9. ~~Явная обработка ошибок БД~~ (частично)
**Исправление:** Добавлен `@app.errorhandler(500)` и шаблон `500.html` с понятным сообщением и ссылкой на главную. Критичные операции по-прежнему можно оборачивать в try/except при необходимости.

### 10. Таймаут и блокировки SQLite
**Где:** `timeout=15.0` и WAL уже заданы.
**Риск:** При длительных запросах или большом числе одновременных записей возможны блокировки.
**Рекомендация:** Держать транзакции короткими; тяжёлые отчёты/экспорт по возможности выносить в фоновые задачи.

### 11. Резервный поток и app context
**Где:** В фоновом потоке используется `with app.app_context():` и внутри `get_setting`/`set_setting`/`do_backup_to_dir`.
**Риск:** При закрытии приложения поток может ещё выполнять код и обращаться к уже закрытой БД.
**Рекомендация:** Использовать флаг остановки (например, `threading.Event`) и по завершении приложения дать потоку время корректно завершиться (или не делать поток daemon и явно его останавливать).

### 12. Секретный ключ и пароли
**Где:** `SECRET_KEY` берётся из `FLASK_SECRET_KEY` или `SECRET_KEY` в окружении; fallback — `"dev-change-in-production"`.
**Рекомендация:** В продакшене обязательно задавать `FLASK_SECRET_KEY` или `SECRET_KEY` через переменные окружения.
